# Sisyphus Agent 独立分叉实施方案

日期：2026-09-08。核查基线：`d6355f11`，根包版本 `0.13.3`。

状态：规划稿。用户已确定名称 Sisyphus Agent；本文件中的技术标识、版本与发布安排是建议默认值，尚未实施。未检查名称、域名、商标或软件包命名空间的可用性。未变更远程仓库、应用配置或用户数据。

命名决策：采用 Sisyphus Agent（单空格），当前定位为个人项目，暂无商业化计划；名称重名暂不作为推进阻塞项。技术标识仍需检查本机冲突；如未来公开发布软件包，再确认相应命名空间是否可用。本文沿用原文件路径以保持已有引用有效。

## 1. 目标与完成定义

把现有 fork 建立为独立维护的 Sisyphus Agent：品牌独立、操作系统应用身份独立、数据与发布独立。保留来源与 Git 历史，继续按需吸收上游修复。

完成意味着：

- 桌面、Web UI、CLI、服务端、安装包、文档与新产生的分享页面统一使用新身份。
- Sisyphus 与上游可同时安装；启动、协议唤起、更新、卸载互不接管。
- 新安装只写入 Sisyphus 自有应用数据；旧数据通过显式导入进入新目录，原始数据保持可回退。
- 发布产物和更新元数据来自维护者控制的渠道；产品服务不再隐式依赖上游基础设施。
- 已验证的平台才能列为正式支持；构建成功不等于安装、迁移与更新验证完成。

本次不增加新的 Agent 功能，不重写运行内核，不清除来源历史，不借改名调整数据库业务语义。

## 3. 已核查的工程事实

| 文件 / 范围 | 当前事实 | 对方案的影响 |

## 4. 品牌独立

### 4.1 产品表面

覆盖 Electron、Web UI、Viewer、marketing、CLI、server 的应用名称与帮助文本，菜单、设置、关于页、窗口标题、系统通知、托盘、错误对话框、OAuth 成功页、Agent 自述与生成文档模板。

替换应用图标、托盘资源、favicon、安装背景和平台图标源。验收小尺寸、深浅背景与 Windows/macOS/Linux 对应产物，不用仅供网页显示的图片替代平台图标资产。

README 保留英文与中文两份；更新贡献指南、问题模板、安全报告入口、主页、支持联系人与新版本说明。历史发行说明和上游贡献链接保留真实来源，不伪装为 Sisyphus 原创历史。

### 4.2 单一身份来源

建立产品身份配置，集中声明 displayName、slug、appId、scheme、目录名和受控服务地址。构建脚本、打包配置与运行时代码读取或从中生成配置，避免 YAML、脚本和源码各自维护不同常量。

按用途区分残留项：必须替换的产品身份、必须保留的原作者归属、版本化兼容项、正常第三方服务示例。建立有理由的允许列表；不能用“源码完全没有 Craft”作为完成标准。

保留 LICENSE 与必要归属记录，核对 NOTICE 和 TRADEMARK 的历史适用范围；新产品展示自己的维护者身份，不能把原作者版权直接改成自己的名字。

## 5. 应用身份独立

- 桌面启动与打包使用一致的 app ID、名称和协议；核对 Windows 安装/卸载标识、快捷方式、通知 AUMID，macOS bundle 信息，Linux desktop 文件与 WM class。
- 核查所有打包入口：根脚本、electron-builder、build-win.ps1、build-dmg.sh、资源准备及安装脚本，统一产物约定。
- 显式管理 Electron userData、sessionData、浏览器 profile、更新缓存、日志、锁文件、IPC/socket 命名，防止沿用旧缓存或单实例锁。
- CLI、服务端与 worker 使用统一新身份。服务端口允许配置；不因改名任意改变网络协议，但需要验证并行启动时能报告端口冲突。
- 环境变量新前缀优先。普通变量可临时读旧别名并给出弃用提示；凭据、数据目录、更新源等敏感边界不自动继承旧值。显式指定旧目录用于正常运行时应拒绝或要求进入导入流程。
- `@craft-agent/*` 内部依赖改名使用单独的机械提交，覆盖 workspace 声明、import、TS alias、bundler external、测试 mock 与 lockfile；兼容性协议不跟随包名盲改。

## 6. 数据独立与迁移

### 6.1 路径边界

桌面、CLI、服务端、worker、凭据、日志和资源播种都通过同一套路径解析访问 Sisyphus 数据。先收拢散落路径，再启用新默认目录。

区分三类路径：

1. 应用拥有的数据：配置、会话、数据库、附件、Artifact、sources、skills、主题、消息网关状态等，迁入新根。
2. 用户外部项目：代码仓库或工作目录，保持原位置，不因改名移动或递归复制。
3. 旧应用管理的外部工作空间：明确选择复制到新位置，或暂不导入；不能让两个应用同时写同一状态库。

### 6.2 导入流程

首次启动提供“全新开始 / 导入现有数据”，CLI 提供同一引擎的显式导入命令。此处是产品迁移交互，不代表已经获得操作本机真实数据的授权。

流程：检测旧目录及自定义路径 → 生成导入清单 → 确认源进程和 worker 已停止 → 一致性快照 → 写入新目录旁的 staging → 路径映射与凭据处理 → 完整性校验 → 同卷原子提交 → 输出不含秘密的迁移报告。

- 旧目录不删除、不重命名、不写入迁移标记。迁移日志、锁和状态存放在目标侧。
- SQLite 必须使用已停止写入后的完整快照或经验证的备份机制；不能只拷贝主库而漏掉 WAL。
- 使用迁移状态机和来源标识支持重试；已有目标不得覆盖，先提供冲突报告。中断只留下隔离 staging，不把半成品作为正常工作区加载。
- 只转换已知结构字段中的应用路径与深链接；不全局替换聊天正文、附件内容或用户脚本。历史绝对链接使用明确映射解析。
- 核对会话 ID、消息、Artifact revision、附件、sources、模型配置、主题、skills、任务和运行记录。文件校验与数据库引用完整性分别检查。
- 自动化、消息网关、后台任务导入后默认暂停，避免旧应用与新应用重复执行、重复发消息；由用户恢复。未知副作用状态保留，不自动重试。
- 已在执行的任务不热迁移。关闭/停止旧任务后导入；旧浏览器登录态和系统加密数据不承诺可移植，必要时重新登录。

### 6.3 凭据

先保留读取旧格式所需的 magic 和派生参数作为兼容实现。通过专用只读导入路径解密旧副本，在目标以新格式版本和新派生命名写入，再验证可读取；普通运行不回退访问旧凭据路径。

不要调用可能自动迁移、修复或重命名源文件的旧加载器直接读取原件。无法解密时明确标记连接需重新授权，不初始化空凭据库来冒充导入成功；其余可迁移内容可保留并报告局部失败。

当前凭据依赖机器身份，同机导入与跨机器搬迁分开验收。新派生名称用于格式隔离，不宣称能够防御同一系统账户中的其他进程。Windows ACL 与 Unix 文件权限分别验证。

### 6.4 回退

导入后两个数据集独立演化。回退是关闭 Sisyphus 后重新使用原应用及其原数据，不是将新数据反向覆盖旧目录。Sisyphus 产生的新内容如需返回旧版，需要另行兼容导出。

## 7. 服务和发布独立

### 7.1 外部依赖清单

| 服务 | 目标行为 | 未就绪时 |
|---|---|---|
| 安装与更新 | 自己的 Release、二进制、元数据和更新缓存 | 显示明确不可用状态，禁止回退上游 |
| 文档与反馈 | 自己的仓库/文档与 issue 入口 | 可以直接使用仓库页面 |
| OAuth relay | 自有部署或各 provider 验证可用的本地回调；同步调整注册信息 | 仅禁用受影响授权方式并解释原因 |
| 分享 Viewer | 自有上传、访问、删除和存储规则 | 禁用新建云端分享，保留本地导出 |
| 遥测 | 默认关闭；如启用，仅使用自有项目与明确配置 | 不注入上游 DSN 或 token |
| 第三方集成 | 保留用户主动配置的官方服务 | 不能按域名把合法 Craft 集成误删 |

逐项核对 OAuth client ID 的来源、适用范围及 provider 要求；不假设所有第三方 client ID 都属于上游，也不批量替换。旧分享链接继续作为历史外链保存，不承诺迁移上游托管内容。

### 7.2 发布路径

建议第一阶段以自有 GitHub 仓库 Releases 承载发布；具体 updater provider、平台 target 与元数据格式在实施时按所用版本官方文档确认。正式域名可后接入，不能阻塞应用身份与本地数据独立。

建设 release workflow：校验 tag/包版本 → 锁定依赖及资源版本构建 → 产物身份检查 → 平台签名/公证（按支持平台落实）→ 生成摘要与更新元数据 → 上传 draft release → 安装和更新验收 → 发布。

- Release 元数据只引用同一版本已验证产物；失败时不提升 latest，不发布半套平台清单。
- 签名证书与发布 token 使用自己的 Secrets，PR 验证无权取得；签名后再生成相应校验数据。
- stable 与 preview 不交叉更新；平台/架构匹配，版本单调递增，禁止引用上游包和旧更新缓存。
- 核查 updater 中“找到缓存安装文件即 ready”的回退行为；品牌隔离之外，还需与可信版本元数据和摘要匹配。
- 用两个 Sisyphus 测试版本实际完成检查、下载、校验、退出安装、重启和数据保留验证。只修改 feed URL 不算更新链路完成。
- 应急回退优先发布更高版本的修复包；不要通过强制降版本回退不兼容的数据结构。
- 未取得签名或平台验收条件时明确标注测试包，不能称为正式发布已完成。

## 8. 顺序、交付物与验收

默认单任务顺序推进，不开启并行 agent。以下是同一个分叉目标中的检查点，均需完成才能宣告正式独立发布。

| 阶段 | 工作 | 交付物 / 放行条件 |
|---|---|---|
| A 身份冻结 | 确认技术身份、清点引用与外部服务、检查本机标识冲突及实际使用的发布命名空间 | 身份配置规范、残留允许列表、外部依赖清单 |
| B 品牌与代码身份 | 图标文案、包/命令、打包身份与路径统一 | 可构建的新品牌包；新安装无旧数据写入；与上游可并存 |
| C 数据导入 | 迁移引擎、凭据兼容、暂停任务、报告与回退 | 合成样本和脱敏副本测试通过；原数据未变 |
| D 服务与发行 | 受控地址、OAuth/分享处理、release workflow 与签名 | 自有 draft release；未就绪服务明确关闭且无上游回退 |
| E 端到端验收 | 安装、导入、协议、worker、更新、卸载 | 验收矩阵有证据；仅声明已测平台支持 |
| F 首次发布 | 中英文说明、来源、迁移指南、已知限制 | 经确认后正式发布并更新仓库身份 |

建议独立提交顺序：身份配置 → 内部包机械改名 → 界面资源 → 应用身份和路径 → 导入引擎 → 服务配置 → 发布流水线 → 文档与验收。避免一个巨大的替换提交掩盖迁移语义。

最低验收矩阵：

| 场景 | 必须验证 |
|---|---|
| 全新安装 | 名称/图标/协议正确，只创建新数据和缓存 |
| 同机并存 | 双方可启动，协议分别唤起，卸载任一方不删另一方数据 |
| 完整导入 | 关键对象数量与引用、附件摘要正确，凭据同机可用 |
| 异常导入 | 中断可重试、目标冲突不覆盖、损坏凭据不清空源、磁盘不足能退出 |
| 数据边界 | 外部项目不移动，不复用上游管理状态，不重复激活自动化 |
| 多入口 | 桌面/CLI/server/worker 使用同一新路径和凭据 |
| 外部服务 | 授权回调、分享和更新仅按配置访问；无上游隐式兜底 |
| 真实升级 | 两个新品牌版本完成升级、重启、数据保留；坏包拒绝安装 |
| 发布产物 | 平台身份、签名状态、元数据、下载地址、版本和摘要一致 |

测试遵循项目约定：先执行迁移、路径、协议、更新配置的聚焦测试；包重命名覆盖多个 workspace，需受影响包的类型检查和生产构建。无需无条件运行全量测试；新增修改或失败再扩大范围。

## 9. 实施前待确定与外部操作边界

不阻塞规划的建议默认值：Windows 首先验收，其他平台以实际设备/CI条件为准；GitHub Releases 为第一发布渠道；域名未就绪时关闭依赖云端的入口；内部命名在首次独立版本中统一。

首次打包前冻结 app ID、数据目录和协议。正式发布前确定发布者署名、支持平台、签名条件以及 OAuth relay / Viewer 的部署选择。

仓库改名、真实数据迁移、删除/覆盖操作、购买域名与证书、启用外部服务和正式发布分别在结果可审阅时取得所需确认。本次规划不执行这些动作。保留用户已确定的名称，不重复询问是否改名。
